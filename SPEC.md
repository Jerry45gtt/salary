# Salary — техническая спецификация MVP

## Стек и границы
- Next.js App Router, TypeScript, React; серверные компоненты для чтения, Server Actions или Route Handlers для изменений. Node.js runtime. Версии зависимостей фиксируются при создании проекта после проверки совместимости.
- Turso (libSQL), серверный клиент @libsql/client и миграции SQL; секреты только на сервере. Локальная разработка может использовать отдельную локальную базу libSQL/SQLite.
- Текущая реализация основы использует Better Auth и Drizzle: таблицы авторизации `user`, `session`, `account`, `verification`, отдельную таблицу `profiles` для валюты. Начальные категории создаются триггером базы при создании пользователя. Восстановление пароля подготовлено через Resend, но его доставка требует настроек и проверки. Production-защита ещё не завершена. Схема ниже описывает функциональные поля и будет уточняться при реализации операций.
- Готовая библиотека аутентификации с проверенной совместимостью с Next.js и Turso: выбор при реализации. Регистрация, вход, безопасное хранение паролей и сброс по email требуют настройки почтового провайдера. Не создавать собственную криптографию или механизм сессий.
- Валидация схемами, например Zod; графики — доступная библиотека, например Recharts, с текстовым представлением. Стили и UI-библиотека выбираются после design.md.

## Модель данных
- `users`: `id` TEXT PK, `email` TEXT UNIQUE NOT NULL, `password_hash` TEXT NOT NULL, `currency` TEXT NOT NULL, `created_at` TEXT NOT NULL; дополнительные таблицы сессий и токенов определяются выбранной библиотекой. Email нормализуется до нижнего регистра.
- `categories`: `id` TEXT PK, `user_id` TEXT NOT NULL FK, `type` TEXT CHECK IN ('income','expense'), `name` TEXT NOT NULL, `archived_at` TEXT NULL, `created_at` TEXT NOT NULL. Уникальность активного имени в рамках пользователя и типа, с нормализацией регистра.
- `transactions`: `id` TEXT PK, `user_id` TEXT NOT NULL FK, `category_id` TEXT NOT NULL FK, `type` TEXT CHECK IN ('income','expense'), `amount_minor` INTEGER NOT NULL CHECK > 0, `date` TEXT NOT NULL в формате YYYY-MM-DD, `comment` TEXT NULL, `created_at` и `updated_at` TEXT NOT NULL. Проверять принадлежность категории пользователю и совпадение типа при каждом изменении; существующей операции разрешается сохранить её архивную категорию.
- ID — случайные UUID. Деньги хранятся целыми минимальными единицами, без float; валюта и число знаков после запятой определяются стандартом валюты. Ввод проверяется на точность и безопасный диапазон целых чисел. Индексы: операции `(user_id, date, id)` и `(user_id, category_id, date)`; категории `(user_id, type, archived_at)`.
- Применять внешние ключи и транзакции БД; проверить их включение и поддержку в выбранном подключении. Даты создания — UTC ISO 8601. Уникальность email и категории обеспечивается БД, а не только интерфейсом.

## Маршруты и действия
- `/register`, `/login`, `/forgot-password`, `/reset-password` — публичные; `/dashboard`, `/transactions`, `/categories`, `/settings` — защищённые.
- Серверные операции: создать/изменить/удалить операцию; создать/переименовать/архивировать категорию; изменить валюту до первой операции. Идентификатор пользователя берётся только из проверенной сессии. Каждое чтение и изменение ограничивается `user_id`; сервер проверяет входные данные и полномочия у источника данных.
- Список: фильтры `from`, `to`, `type`, `category`, курсор `(date,id)` и ограничение 50; порядок `date DESC, id DESC`. Отчёты агрегируются на сервере по тем же фильтрам периода. Удаление категории не допускается в MVP.
- После успешного изменения инвалидировать соответствующие данные и обновлять экран; не кэшировать персональные данные как общедоступные. Ошибки возвращаются без внутренних подробностей, ввод сохраняется при ошибке формы.

## Защита и эксплуатация
- Cookies сессии: HttpOnly, Secure в production, SameSite и срок жизни согласно библиотеке. Проверка авторизации на сервере для каждого доступа, защита от CSRF согласно механизму библиотеки/фреймворка, лимиты попыток входа и сброса пароля на сервере.
- Пароли хешировать рекомендуемым библиотекой алгоритмом; токены восстановления одноразовые и ограничены по времени, хранить безопасно. Не логировать пароли, токены, комментарии или финансовые данные.
- Переменные окружения для URL и токена Turso, секрета авторизации, адреса приложения и почтового сервиса; пример без секретов хранить в `.env.example`. Настроить HTTPS, отдельные базы для разработки и production, резервное копирование и проверку восстановления.
- Доступность: семантические формы, подписи, фокус, клавиатурная навигация, достаточный контраст, графики с табличной альтернативой. Адаптивность проверяется на узких и широких экранах.

## Проверка
Проверить валидацию сумм и дат, расчёты, пустые интервалы, границы периода, архивирование, пагинацию и разграничение данных двух пользователей; отдельно пройти регистрацию, восстановление пароля и CRUD в браузере. Перед публикацией выполнить lint, проверку типов, тесты и production-сборку.
