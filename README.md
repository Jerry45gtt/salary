# Salary

Основа приложения для личного учёта доходов и расходов. Документы с требованиями и планом: [PRD](PRD.md), [SPEC](SPEC.md), [дизайн](design.md), [задачи](tasks.md).

## Запуск для разработки

Требуется Node.js и npm.

```bash
npm install
npm run db:migrate
npm run dev
```

Откройте http://localhost:3000. Для локальной разработки создайте `.env.local` с `BETTER_AUTH_URL=http://localhost:3000` и случайным `BETTER_AUTH_SECRET` длиной не менее 32 символов. Можно создать секрет командой `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`. Не передавайте его другим людям и не публикуйте.

Без `TURSO_DATABASE_URL` используется локальный файл `local.db`, который не попадает в Git. Для Turso укажите `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` в `.env.local`, затем выполните `npm run db:migrate`; команда изменит указанную базу, поэтому используйте отдельную базу для разработки. Переключение на Turso не переносит данные из `local.db`: это отдельные базы. Для production необходимы отдельные URL и токен, секрет и корректный публичный `BETTER_AUTH_URL`. Начальная схема использует идемпотентный SQL, а не полноценную систему версионирования миграций.

Доступны регистрация, вход, выход, управление категориями и добавление, изменение и удаление операций. При регистрации создаются категории по умолчанию. Список операций поддерживает фильтры и переход по страницам. До первой операции в настройках можно выбрать UZS, USD, EUR или RUB; затем валюта фиксируется, в том числе после удаления операций. Там же можно переключить светлую и тёмную тему; выбор сохраняется в текущем браузере. На экране обзора доступны суммы и графики за выбранный период длиной до 100 лет. Текущий месяц определяется по часовому поясу Asia/Tashkent.

Для восстановления пароля зарегистрируйте почтовый сервис [Resend](https://resend.com/docs/send-with-nodejs), подтвердите домен отправителя и укажите в `.env.local` значения `RESEND_API_KEY` и `EMAIL_FROM` (например, `Salary <noreply@example.com>` с вашим подтверждённым доменом). Не отправляйте API-ключ в переписку. Перезапустите сервер после изменения настроек. Без этих настроек страница восстановления сообщает, что почта не настроена. После подключения необходимо проверить отправку и переход по ссылке; ссылка действует один час и при смене пароля существующие сессии отзываются. Обработка запроса к почтовому сервису ограничена по времени; при ошибке в журнал попадает только общее сообщение, без письма и ключа.

Идентификаторы ссылок восстановления хешируются при хранении. После включения хеширования ранее созданные ссылки становятся недействительными: при необходимости запросите новую ссылку.

Публичный запуск до проверки доставки писем, Turso и защиты не предусмотрен. Ограничение запросов авторизации хранится в базе и доступно всем экземплярам, использующим одну Turso. В production без `SALARY_CLIENT_IP_HEADER` применяется общий лимит для всех пользователей одного маршрута: это может блокировать вход другим пользователям. Для индивидуальных лимитов укажите имя отдельного заголовка, который ваш доверенный прокси всегда перезаписывает проверенным IP клиента; сервер приложения должен быть недоступен напрямую. Не используйте клиентский заголовок, `Forwarded` или `X-Forwarded-For`. Перед запуском проверьте правила сети и заголовков на выбранной платформе. Сначала применяйте миграции, затем запускайте новую версию приложения.

`GET /api/health` возвращает только `{"status":"ok"}` при доступности базы и наличии необходимых таблиц или `503` при ошибке; ответы не кешируются. Его можно подключить к мониторингу доступности после размещения. Он не проверяет отправку писем, резервные копии или корректность всех данных и не заменяет отдельную проверку этих сервисов.

Проверки: `npm run lint`, `npm run typecheck`, `npm run build`. При запущенном сервере и локальной базе можно последовательно выполнять `node scripts/check-auth.mjs`, `node scripts/check-categories.mjs`, `node scripts/check-filters-settings.mjs`, `node scripts/check-report.mjs`, `node scripts/check-reset.mjs`, `node scripts/check-rate-limit.mjs`. Эти сценарии отказываются запускаться при указанной удалённой базе; убедитесь также, что сам сервер перезапущен с локальной конфигурацией `file:local.db`. `node scripts/check-health.mjs` проверяет запущенный сервер. Настройку заголовков проверяет `node scripts/check-ip-config.mjs`. Тесты используют временные аккаунты и не должны выполняться на production. Из-за ограничения попыток входа при быстром повторении может потребоваться подождать минуту.

Для отдельной тестовой базы Turso `node scripts/check-turso.mjs` проверяет подключение и наличие таблиц, а `node scripts/check-turso-app.mjs` создаёт и затем удаляет два временных аккаунта и одну тестовую операцию. Последний скрипт требует `SALARY_TEST_DATABASE_CONFIRMED=1`: задавайте его только после проверки, что сервер и скрипт используют одну и ту же **тестовую**, не production-базу. Текущая `.env.local` подключена к выбранной production-базе, поэтому для разработки и тестов сначала настройте отдельную базу. План оставшейся подготовки — в [launch-checklist.md](launch-checklist.md). Переменные перечислены в `.env.example`; не сохраняйте настоящие секреты в репозитории.

`node scripts/check-reset-email.mjs` проверяет подготовку запроса к Resend и обработку ошибок с имитацией сервиса. Реальные письма он не отправляет и успешную доставку не подтверждает.

Для локальной базы доступна проверка копирования и восстановления `node scripts/check-backup.mjs`. Команды и ограничения для локальных копий и Turso описаны в [backup-guide.md](backup-guide.md).

Подготовка и последовательность размещения на Vercel описаны в [vercel-guide.md](vercel-guide.md).
