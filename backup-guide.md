# Резервные копии и восстановление Salary

## Что уже проверено
Скрипт `node scripts/check-backup.mjs` создаёт временную локальную SQLite-базу только с тестовыми данными, делает копию и восстанавливает её в отдельный файл. Затем проверяет целостность, сумму операции, блокировку валюты и отказ от перезаписи существующей копии. Тестовые файлы удаляются после проверки. Проверка не обращается к настоящей базе Turso и не подтверждает работу удалённого восстановления.

## Локальная база разработки
Для копирования локального SQLite-файла требуется Node.js с `node:sqlite` и `sqlite.backup` (Node.js 22.16+ или 23.8+). Из каталога проекта:

```bash
node scripts/backup-local.mjs local.db my-backup.db
```

Первый путь — существующая локальная база; второй — **новый** файл копии. Скрипт проверяет целостность до и после копирования и не перезаписывает существующий файл. Он предназначен только для локального файла SQLite, а не для URL или токена Turso. Для проверки восстановления создайте из копии ещё один новый файл этой же командой и подключите отдельное тестовое окружение к нему; не заменяйте рабочую базу во время работы приложения.

Файлы копий содержат личные финансовые данные, email, хеши паролей и данные сессий. Храните их в зашифрованном хранилище с ограниченным доступом, задайте срок хранения и не отправляйте в Git, логи или общий чат. Расширение `.db` исключено из Git; если выбрать другое расширение или расположение, защиту необходимо проверить отдельно. Права файла на Windows зависят от настроек каталога и системы.

## Восстановление Turso к выбранному моменту
Turso поддерживает point-in-time recovery: восстановление создаёт **новую** базу из существующей на выбранное время. Период доступного восстановления зависит от тарифа; проверьте действующие условия до запуска и запишите желаемые сроки хранения. Такой способ не заменяет независимые резервные копии и не восстанавливает обычным PITR уже удалённую базу. [Документация Turso](https://docs.turso.tech/features/point-in-time-recovery).

1. Определите исходную базу и момент до повреждения. Время указывается в RFC 3339, например `2026-11-18T12:00:00Z`; `Z` означает UTC.
2. Подготовьте отдельное имя для восстанавливаемой базы и проверьте квоту. Пример команды из документации:

   ```bash
   turso db create salary-recovery-test --from-db salary-production --timestamp 2026-11-18T12:00:00Z
   ```

   Это пример: замените имена и время на реальные и сначала убедитесь, что операция доступна вашему тарифу. [Параметры команды](https://docs.turso.tech/cli/db/create).
3. Для новой базы получите отдельный URL и токен. Подключите их только к изолированному тестовому окружению; не сохраняйте токены в репозиторий.
4. Проверьте схему и миграции, количество записей и важные сценарии тестовым аккаунтом. Не отправляйте настоящие письма и не подключайте проверочное окружение к производственным интеграциям.
5. Если требуется вернуть приложение в работу после аварии, отдельно согласуйте момент переключения и возможную потерю записей после выбранного времени. Переключайте настройки production только после проверки восстановленной базы и контрольной копии текущего состояния. Старую базу не удаляйте до завершения проверки и принятого решения о хранении.

Для отдельного экспорта Turso предоставляет `turso db export`, но документация предупреждает, что файл может не содержать последние изменения. Поэтому сначала определите приемлемую потерю данных и проверьте актуальные инструкции Turso по синхронизации экспортированного снимка. [Документация экспорта](https://docs.turso.tech/cli/db/export).

## Перед запуском
Выбрать ответственного за копии и восстановление, периодичность и срок хранения, защищённое место хранения и допустимую потерю данных; выполнить пробное восстановление именно на реальной конфигурации Turso и записать результат. Автоматизация копирования, облачное хранилище и мониторинг в проекте пока не настроены.
